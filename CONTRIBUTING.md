# Codebase Overview for Contributors

Welcome! This section will help you quickly understand how Metaform is structured and how it works before you make your first contribution.

---

## What is Metaform?

Metaform is a TypeScript library that provides a typed, zero-dependency interface to the [AniLiberty](https://aniliberty.tv/) REST API. It ships no third-party runtime packages and relies solely on the native `fetch` and `URL` APIs, making it compatible with both Node.js and modern browsers out of the box.

## Repository Layout

```
│   ├── index.ts              # Public entry point — exports API functions
│   ├── bundle.ts             # Full bundle entry (index + scheme + transport + version-map)
│   │
│   ├── api/
│   │   ├── version-map.ts    # Registry of all versioned endpoints (guard + mapper + serializer + path)
│   │   └── functions/        # One file per API call (getTeams, getMediaVideos, etc.)
│   │       └── __tests__/    # Tests for each function
│   │
│   ├── scheme/
│   │   └── v1/               # All type definitions for API version 1
│   │       ├── teams/        # Endpoint-specific module (types, guards, mapper, serialize-params)
│   │       │   ├── roles/    # Nested resource — same internal structure
│   │       │   └── users/    # Nested resource — same internal structure
│   │       └── media/
│   │           └── videos/   # Same internal structure
│   │
│   ├── helpers/
│   │   └── type-helpers.ts   # Primitive type guards (isOptionalString, isUuid, isRecord, etc.)
│   │
│   └── transport/
│       ├── types.ts          # Transport interface definitions
│       ├── fetch-transport.ts # Default implementation using native fetch
│       └── index.ts
│
├── tsdown.config.ts          # Build configuration (tsdown, outputs ESM + CJS)
├── vitest.config.ts          # Test runner configuration
├── tsconfig.json             # Base TypeScript config
├── tsconfig.lib.json         # Config used during library build
└── package.json
```

The `dist/` directory (generated by the build, never committed) mirrors `src/` and ships four separate entry points alongside `.d.ts` declaration files for both ESM and CJS consumers.

## Architecture Principles

### 1. Transport is a replaceable interface

HTTP communication is abstracted behind a `Transport` interface:

```typescript
interface Transport {
  request<T>(req: RequestTransport): Promise<TransportResponse<T>>
}
```

The default implementation (`createFetchTransport`) wraps the native `fetch`. Any consumer can substitute their own transport — for example, to inject authentication headers, use `axios`, or mock requests in tests — without touching library code. This is the main extension point of the library.

### 2. Every endpoint is defined once in the version map

`src/api/version-map.ts` is the single source of truth for all supported endpoints. Each entry in the map bundles together four things:

- **`guard`** — validates that the raw API response has the expected shape
- **`mapper`** — transforms the raw DTO into the library's internal type
- **`serializeParams`** — converts typed query params into a `Record<string, string>` for the URL
- **`path`** — the API endpoint path string

This structure means adding a new endpoint never requires changes to the request pipeline — only a new entry in the map and a corresponding scheme module.

### 3. Each endpoint's scheme lives in its own module

Every endpoint under `src/scheme/v1/<resource>/` contains exactly four files:

| File                  | Responsibility                                                          |
| --------------------- | ----------------------------------------------------------------------- |
| `types.ts`            | TypeScript interfaces for both the raw DTO and the mapped internal type |
| `guards.ts`           | Runtime type-guard functions that validate a raw API response           |
| `mapper.ts`           | Pure function that transforms a validated DTO into the internal type    |
| `serialize-params.ts` | Pure function that converts typed params into a URL query string        |

The internal types follow a consistent contract: every field is always present and is either a concrete value or `null`. The raw DTO types reflect the actual API, where fields may be `undefined` (absent). The mapper is the boundary between these two worlds.

### 4. API functions are thin and generic

Functions in `src/api/functions/` are almost purely plumbing. A typical call looks like:

```typescript
export async function getTeams<V extends keyof VersionMap>(
  transport: Transport,
  version: V,
  params?: TeamsParams<V>,
): Promise<TeamsResult<V>>
```

The generic `V` parameter lets TypeScript infer the exact return type and params type from the version you pass in — no casting needed by the caller. The function itself just pulls `guard`, `mapper`, `serializeParams`, and `path` from the version map, makes the request, validates the response, and returns the mapped result.

### 5. Type guards protect the runtime boundary

`src/helpers/type-helpers.ts` provides small, composable primitive guards (`isOptionalString`, `isValidNumber`, `isUuid`, `isRecord`, etc.). Guard functions in `src/scheme/<version>/<resource>/guards.ts` compose these primitives to validate a complete DTO. If the API returns an unexpected shape, the guard throws an error at the boundary rather than letting a malformed object leak into the rest of the application.

## Build System

The project uses [tsdown](https://github.com/rolldown/tsdown) (a TypeScript-aware wrapper around Rollup/esbuild) to produce two build outputs:

- **`dist/`** — four tree-shakeable entry points (ESM + CJS, with `.d.ts` declarations):
  - `@maxqwars/metaform` — API functions
  - `@maxqwars/metaform/scheme/v1` — all v1 types and utilities
  - `@maxqwars/metaform/transport` — transport interface and `createFetchTransport`
  - `@maxqwars/metaform/version-map` — the versioned endpoint registry
- **`dist-bundle/`** — a single ESM bundle (`src/bundle.ts`) that re-exports everything at once, useful for environments where tree-shaking isn't available.

## Adding a New API Endpoint — Checklist

1. Create a new scheme directory under `src/scheme/v1/<resource>/` with four files: `types.ts`, `guards.ts`, `mapper.ts`, `serialize-params.ts`, and an `index.ts` barrel export.
2. Add the endpoint to `src/api/version-map.ts` — plug in the guard, mapper, serializer, and path.
3. Create `src/api/functions/get-<resource>.ts` following the pattern of existing functions.
4. Export the new function from `src/index.ts`.
5. Write tests for the guard, mapper, serialize-params, and the function itself (place them in the corresponding `__tests__/` folders).
6. Run `pnpm check` (typecheck + tests + build) before opening a pull request.

## Running the Project Locally

```bash
# Install dependencies
pnpm install

# Build the library
pnpm build

# Watch mode (rebuilds on every save)
pnpm dev

# Run tests
pnpm test

# Run tests with coverage
pnpm test:coverage

# Type-check
pnpm typecheck

# Lint
pnpm lint

# Format source code
pnpm format
```
